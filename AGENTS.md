## Product Brand Rules

### Mandatory naming standard

Never default to literal, descriptive product names that simply restate what the product does.

Reject generic “AI startup” names, buzzword compounds, and predictable suffixes or prefixes such as AI, Bot, Gen, GPT, Nexus, Nova, Verse, -ify, or random X/Z styling unless the concept genuinely earns them.

Prefer a short, distinctive, memorable, pronounceable, and ownable name that can become associated with the product over time instead of explaining the product immediately.

The brand should have room to grow beyond the first feature or category. Use names such as Facebook, X, and WhatsApp as the naming principle: the identity becomes meaningful through the product rather than reading like a feature label.

Avoid generic AI identity symbols such as robot heads, brains, circuit marks, chat bubbles with sparkles, and stock gradient logos unless the user explicitly requests them.

Before recommending a final name, check current product-name collisions, domains, trademarks, and major social handles when practical. Never claim availability without verifying it.

When presenting candidates, explain the concept, sound, memorability, expansion potential, and possible risks. Do not pad the list with weak names.

This standard is mandatory for future product naming and branding work for Ahmard.

## UI and Frontend Work

### Mandatory UI workflow

For website, web app, dashboard, landing page, product interface, or other visual frontend work, use the web-design-engineer skill.

Before implementing material UI changes:

1. Inspect the existing project and its current visual language.
2. Read and follow the web-design-engineer skill.
3. Establish a coherent visual direction and design system before implementation.
4. Study appropriate production references when useful.
5. Use deliberate layout and component patterns instead of defaulting to generic AI-generated SaaS styling.
6. Apply responsive design, accessibility, interaction polish, appropriate motion, and visual consistency.
7. Review the rendered result and polish obvious issues before considering the UI complete.

Avoid arbitrary values, random styling, decorative clutter, unnecessary gradients, copied-looking templates, and generic “vibecoded” presentation.

Do not depend on ui.md. The web-design-engineer skill is the authoritative workflow for visual frontend and UI work.

Do not duplicate the detailed UI methodology in this file. Follow the specialized skill instead.

### UI component resources

When building a UI component, check the project's existing component library first, then check Spectrum UI when appropriate.

Use Spectrum UI as a component resource:

https://ui.spectrumhq.in

If the Spectrum UI MCP is available, use it to search and retrieve suitable components. Otherwise, use Spectrum UI's documented component source and installation instructions.

Do not force Spectrum UI into a design when it conflicts with the project's established visual direction.

Never recreate a common component from scratch without first checking the existing project components and Spectrum UI.
